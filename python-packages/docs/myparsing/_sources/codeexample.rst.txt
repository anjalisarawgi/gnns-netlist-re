===============
Parsing Example
===============

Example of how to parse an already synthesized netlist.

Parsing Process
---------------

Parsing includes all tools that internally use `tmp.parse_to_obj` method and therefore still operate on the synthesized verilog code and not on graphs. 

Graph Creation
^^^^^^^^^^^^^^

In a first step the parser takes the verilog code and generates an abstract syntax tree (ast). In a second step this ast is converted into a graph structure.

**Alternative 1:** 

You can directly parse the netlist into a gml graph format (this command works if you are in the same folder as used for the synthesis):

.. code-block:: bash
    
    verilog2graph qflow/postprocessed/name_of_synthesized_file.v --output_format gml --output_info complete_data --do-not-zip -o graph

If you inspect the generated file(s) in the directory graph, you will find a .gml file for each of your parsed netlist files.

Remarks: 

* The meta data and annotations can only be generated and saved in the gml structure. Additionally, the flag `--output_info complete_data` needs to be set there.

* After synthesizing multiple depending files the main verilog file, e.g. `main_file.v`, contains the whole synthesized design. You can use this verilog file to generate the graph of the whole design. If the synthesis outputs of the individual submodules should be converted into graph structures, replace the path to a single file by a path to the folder that contains all files in the command above.

* Parsing multiple synthesized verilog files that are independent of each other is possible by replacing the path to a single file by a path to the folder that contains all files.

If only the nodes and the interconnections of the graph should be created and no annotations should be added, use this adaption:

.. code-block:: bash
    
    verilog2graph qflow/postprocessed/name_of_synthesized_file.v -o graph

The output is a text file containing all the nodes and the interconnections of the graph. 



Remark: The text file could, e.g., be used for the clustering procedure.


**Alternative 2:** 

If not only the resulting graph structure from Alternative 1 is desired you can also inspect the netlist with python at many abstraction levels.

The following commands could be used for processing your netlist using a python environment.
To execute them in the current bash session, first activate the interactive python shell.

If you are working in a virtual environment use:

.. code-block:: bash
    
    python

else additionally specify that you would like to use python 3:

.. code-block:: bash
    
    python3

To close the interactive python shell just use this command:

.. code-block:: bash
    
    quit()

Below are examples of commands for the interactive python shell:

The verilog file can be converted into a python object representing a graph structure:

.. code-block:: python
    
    import tueisec_myparsing.myparsing_ply as tmp
    O = tmp.parse_to_obj("qflow/postprocessed/name_of_synthesized_file.v", "/nas/ei/share/sec/tools/qflow/qflow-1.3-RE/share/qflow/tech/osu035/osu035_stdcells.lib", add_const_as_input=True)

Remark: Internally first the verilog code is converted into an abstract syntax tree (ast). Based in the ast further information are generated.

You could use some of the following commands to interact with the O object and extract further information:

Get the abstract syntax tree (ast) of the verilog code:

.. code-block:: python
    
    O.ast 

The verilog ast is a simple hierarchical representation of the file's structure. It will e.g. have the module on one layer followed by a layer of all standard gates (OR, AND, ...) it contains and a layer with all pins (inputs and outputs of the gates). The relation of elements in different layers is represented by cross-layer interconnections. 

Sometimes an adaption of the verilog file is wanted. It is then easier to modify the ast object than operating on the verilog file itself. 

Remark: The ast will additionally be used in an intermediate step when generating the O object. For further information on the ast see


After changing the verilog ast it can be converted back into a verilog file:

.. code-block:: python
    
    from tueisec_myparsing.codegen import ASTCodeGenerator
    generator = ASTCodeGenerator()
    rslt = generator.visit(O.ast)
    with open("modified_file.v", "w") as outfile:
        outfile.write(rslt)

You can look at the generated file when you are done working in the interactive shell. It contains a modified version of the verilog code from the original file.

Access other easier data structures of the O object:

Dictionary of input nodes of O:

.. code-block:: python
    
    O.in_nodes

Dictionary of output nodes of O:

.. code-block:: python
    
    O.out_nodes

Dictionary of other nodes of O with metadata:

.. code-block:: python
    
    O.other_nodes

Dictionary of nets in design:

.. code-block:: python
    
    O.nets 

The nets are connected wires on the same voltage level. All input, output and other wires go into or out of a gate of the design. Therefore, these wires all drive one or multiple receivers, carrying information through the circuit. The output is a dictionary containing a list of driven nodes for each net. The output is, e.g., `["net_a": ["AND2X1", "DFFPOSX1" ...], "net_b": ...]`.

Dictionary of drivers for nets:

.. code-block:: python
    
    O.net_drivers

The dictionary of net drivers contains all nodes that drive the nets by supplying an output voltage. It does map the nets from above to the corresponding net drivers.

Get the module name as a string:

.. code-block:: python
    
    O.module_name

Dictionary of the standard cell type of each node:

.. code-block:: python
    
    O.node_types

Simple dictionary explaining the edge relations between nodes, no fancy data there:

.. code-block:: python
    
    O.graph

Inspect the cell library that was used in the synthesis step:

.. code-block:: python
    
    O.cell_lib

In the parsing process the standard cell library will be automatically imported and provides a possibility to check for the functionality and content of single standard cells.  
A dictionary containing all the important info from /nas/ei/share/sec/tools/qflow/qflow-1.3-RE/share/qflow/tech/osu035/osu035_stdcells.lib is generated.

Check whether the standard cell AND2X1 is a FlipFlop:

.. code-block:: python
    
    O.cell_lib["AND2X1"].get("ff")

Returns None, i.e., standard cell AND2X1 is not a FlipFlop.

Check whether the standard cell DFFSR is a FlipFlop:

.. code-block:: python
    
    O.cell_lib["DFFSR"].get("ff")

Returns `{'next_state': 'D', 'clocked_on': 'CLK', 'clear': '(!R)', 'preset': '(!S)', 'clear_preset_var1': 'L'}`, i.e. standard cell DFFSR is a Flip-Flop.

Get information on the pin Y of the standard cell AND2X1:

.. code-block:: python
    
    O.cell_lib["AND2X1"]["Y"] 

Returns `{'direction': 'output', 'function': '(A&B)'}`, i.e. pin Y is an output pin and has the function `A and B`. A, B are the inputs of this cell.

The graph structure of O.graph is a very simple and primitive representation of the hierarchy of the verilog file. This representation could be extended with further annotations. Each wire could be annotated by adding the information to which ports it is connected to. To all gates the Boolean logic they represent could be added. This annotated graph is the networkx-graph.

Directly generate the networkx-graph (same procedure as with the command line tool `verilog2graph` from alternative 1): 

.. code-block:: python
    
    G = O.get_networkx_graph(complete=True) 

You can get the same graph by parsing the .gml file created before:

.. code-block:: python
    
    import networkx as nx
    G = nx.read_gml("graph/name_of_synthesized_file.gml")

Remark: Going from G to `*.v` again should be possible, but has not been implemented before. It would be OK if you stick to O.ast!

Close the interactive python shell:

.. code-block:: python
    
    quit()

As previously mentioned, you can now look at the generated file: 

.. code-block:: bash
    
    vim modified_file.v 

Close the file again:

.. code-block:: bash

    :q

Hierarchy Generation
^^^^^^^^^^^^^^^^^^^^

The generation of the hierarchical structure belongs to the parsing process. The parsing of the verilog file is done internally. 

The main procedure to generate a hierarchy is the following. First the logging file that was generated during the synthesis process is used. Here the units of the main_file.v are determined by identifying the names of all submodules that were needed for synthesizing the main module. These names are the names that were used in the un-synthesized main_file.v. The synthesized design main_file.v still contains these submodule names as module prefixes. Therefore, the standard cells of the synthesized design, i.e., the nodes of the graph, can be assigned to the modules they belong to using these prefixes. The output is a list of nodes that are assigned to the different modules.

To generate hierarchical data, you need some ingredients:

a) The logfile from yosys

b) The top-level netlist (the whole design, not some sub-design)

c) The `run_hierarchy` command

Then it's simple.

Generate hierarchical data:

.. code-block:: bash

    run_hierarchy qflow/postprocessed/name_of_synthesized_file.v -D qflow -L qflow/log/synth_name_of_synthesized_file.log -u osu035 -o qflow/hierarchy
    
Remark: The path after flag -L is the path to the log-file that was generated during the synthesis process.

Look at the hierarchy at `qflow/hierarchy` :

.. code-block:: bash
    
    cd qflow/hierarchy
    vim hierarchy_(modules_)name_of_synthesized_file.csv
    :q

Further procedure
-----------------

The generation of the graph as a text file from the graph generation section and the hierarchical data from the hierarchy generation section can, e.g, be used further for the clustering process.
